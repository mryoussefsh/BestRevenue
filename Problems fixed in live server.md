## 1. Auto Sync Runs One Time Only (Scheduler Check Failing)

### 📌 Problem Details
The dynamic Google Ad Manager (GAM) sync scheduled command (`gam:sync`) ran successfully on its first execution but failed to trigger again on subsequent scheduled runs, even when set to run hourly.

### 🔍 Root Cause
1. **Negative Differences**: Carbon's `diffInMinutes()` function returned a negative integer because the last run timestamp was in the past. Since a negative number is never greater than or equal to a positive interval (e.g. `-60 >= 60` is `false`), the command always assumed it was "not due yet" and skipped execution.
2. **Cron Execution Delay**: When the server cron is configured to run at exact hourly boundaries, minor execution delays or framework bootstrap time could cause the exact time difference to be slightly less than 60 minutes (e.g., 59 minutes and 58 seconds). Carbon's `diffInMinutes()` truncates decimal values to the nearest integer, resulting in `59` instead of `60`, which also skipped the run.

### 🛠️ Fix Applied
- Replaced `diffInMinutes()` with `abs(diffInSeconds())` to guarantee a positive difference comparison.
- Introduced a **30-second grace buffer** (checking against `$interval * 3600 - 30` seconds) to accommodate minor cron execution delays.

## 3. Website Tracking Script Check Failing & Made Frequency Dynamic

### 📌 Problem Details
Active websites with the tracking script correctly installed were still scanned and marked as `Missing` by the crawler check. Additionally, there was no way to change the tracking check frequency (it was hardcoded to run exactly once an hour).

### 🔍 Root Cause
1. **User-Agent Block/WAF Challenges**: The validation command `tracking:verify` used a custom user agent string (`tracking-validator/1.0`). Web Application Firewalls (WAFs) like Cloudflare and plugins like Wordfence or LiteSpeed Cache on target publisher websites frequently block or challenge non-standard browser user agents coming from server IPs, returning `403 Forbidden` or `401 Unauthorized` responses and failing the scan.
2. **Missing Trailing Slash**: The URL check did not append a trailing slash `/` to domain names, causing some servers to return redirect responses (301/302), which in some cases could get blocked or loop.
3. **Hardcoded Cron Interval**: In `routes/console.php`, the verification was hardcoded to run exactly `hourly()`, with no admin settings mapping.
4. **IP-Based WAF Blockage on Hosting Datacenter**: Some publisher websites block all automated requests originating from hosting datacenter IPs (like Hostinger or AWS) even when using standard browser User-Agents (like Chrome). However, they whitelist common system tools and bots (like WordPress, Googlebot, or Bingbot).
5. **Universal Datacenter IP Blocks (False Negatives)**: In strict environments, target firewalls may block the host IP entirely (returning `403 Forbidden` or returning a `200 OK` WAF block page) regardless of headers/User-Agents. When the automated scan was blocked, it was falsely marked as `missing`, overriding the valid `active` status generated by real user traffic.

### 🛠️ Fix Applied
- **Multi-Agent Fallback Crawler**: Implemented an iterative fallback strategy that tries multiple canonical URLs and distinct User-Agents (Chrome, WordPress core user-agent, Googlebot, Bingbot, Safari) along with standard browser request headers (Accept, Accept-Language, Cache-Control) to guarantee successful bypass of IP-based datacenter firewalls.
- **WAF Bypass & Status Safety Fallback**: Enhanced the scanner to distinguish between a *genuine missing script* (successful response but script is absent) and a *firewall block / connection error* (all queries return non-2xx status, timeouts, or WAF block pages). If the scan is blocked or unreachable, the system now **preserves the existing status** (e.g. `'active'`) instead of falsely downgrading it to `'missing'`.
- **WAF Block Page Parser**: Integrated a parser to check successful (`200 OK`) responses for common security/WAF signatures (Cloudflare, Wordfence, LiteSpeed, Sucuri, "Access Restricted" translations, etc.) to ensure block pages are not falsely marked as "script missing."
- **Real Traffic Fallback (Final Safety Net)**: When the crawler is blocked by a WAF/firewall from all IPs and all user agents, the system now queries the `traffic_hourly_stats` table for real visitor traffic in the **last 48 hours** for that specific website. If real visitors have triggered the tracking script, the site is automatically promoted to `'active'`. This works because the `publisher-tracker.js` snippet in the publisher's pages calls our own `/api/v1/track` endpoint on every page load, and that endpoint updates `tracking_status = 'active'` in real time.
- **Dynamic Scheduler**: Gated the command execution using new admin settings: `tracking_verify_frequency` (daily, hourly, minutes) and `tracking_verify_interval`, stored in the database and cache, similar to the GAM Sync schedule.
- **Consolidated Error Logging**: Aggregated the status code / exception logs of all fallback configurations and logs a single unified warning to the admin if and only if all configuration combinations failed to locate the tracking script. This avoids cluttering logs during multi-agent scanning.
- **Branding & Layout Configuration**: Updated the frontend and backend settings controller to dynamically validate, order, and render these new configuration inputs.

## 4. Tracking Beacon Sent to Wrong Server (Critical Root Cause)

### 📌 Problem Details
Publisher websites showed high real traffic, the tracking code was correctly installed in the page source, but the system **never auto-updated** the tracking status to `active`. The `/api/v1/track` beacon was being sent to the **publisher's own server**, not to the BestRevenue server.

### 🔍 Root Cause
`publisher-tracker.js` used a **relative URL** `fetch('/api/v1/track', ...)`. When a publisher embeds this script on their own domain (e.g. `crypto.fastcars1.com`), the browser resolves the relative path against the **publisher's domain**, sending the beacon to `https://crypto.fastcars1.com/api/v1/track` instead of `https://your-bestrevenue-server.com/api/v1/track`. The BestRevenue server never received any tracking pings, so:
- `tracking_status` was never auto-set to `active` by `TrackingController`
- `traffic_hourly_stats` had no records for the website
- The fallback traffic check in `tracking:verify` also found no traffic
- Result: status stuck as `missing` despite the code being correctly installed and traffic flowing

### 🛠️ Fix Applied
- **Auto-detect API Base from Script `src`**: Updated `publisher-tracker.js` to extract the server origin from its own absolute `src` URL (`new URL(s.src).origin`). The beacon now always targets the correct BestRevenue server, regardless of which publisher domain the script runs on.

## 5. Real-time Traffic Monitor Showing 0 & On/Off Toggle (Shared Hosting Fallback)

### 📌 Problem Details
On shared hosting (like Hostinger) without Redis support, the real-time visitor count always showed `0` even when websites had active traffic. Additionally, there was no toggle to turn the tracking system on or off.

### 🔍 Root Cause
1. **Redis Dependency**: The real-time traffic system was designed to write exclusively to Redis inside a queued job `ProcessTrafficEventJob`. In shared hosting setups, Redis is unavailable and queue workers cannot run persistently. While there was a MySQL fallback in `AdminTrafficController::realtime()`, it attempted to read from `traffic_hourly_stats` which was never populated, and specifically from `active_visitors_peak` which remained `0` because the tracking controller did not update it during MySQL fallback.
2. **Missing Toggle**: There was no settings entry to enable or disable the traffic tracking script globally, making it impossible to stop recording traffic without deleting/modifying the tracker script on publisher sites.

### 🛠️ Fix Applied
- **Laravel Cache Fallback**: Developed a file-based Cache fallback system in `TrafficService.php` that emulates Redis sets/HyperLogLogs to track active visitors over a sliding 30-minute window, hourly/daily unique visitors, and country/referrer/browser visit distributions.
- **Tracking Controller MySQL Branch**: Updated `TrackingController::track()` to resolve visitor metadata early and update cache aggregations and write directly to `traffic_hourly_stats` (incrementing visits, updating unique visitors, and setting `active_visitors_peak` dynamically) when Redis is not available.
- **Admin Dashboard Integration**: Updated `AdminTrafficController.php` to fetch active visitors and country/referrer metrics from the new Cache fallback when Redis is offline.
- **Daily Aggregation Support**: Modified `BuildDailyTrafficSummaryJob.php` to build daily summaries using database hourly stats and Cache aggregates instead of querying Redis.
- **Global Toggle Setting**: Added a `traffic_tracking_enabled` setting (migration + SettingController validation and boolean casting normalization) that allows administrators to turn tracking ON or OFF. When OFF, the track endpoint returns `204 No Content` immediately.
- **Automated Tests**: Added end-to-end integration tests in `TrafficFallbackTest.php` to verify fallback functionality and settings toggle operation.

## 6. Stuck Period Closing and Auto-Close Scheduler Failure (Shared Hosting Fallback)

### 📌 Problem Details
On shared hosting (Hostinger), manual period closing triggers got permanently stuck in the `closing` status. In addition, the auto-close scheduled period command failed to trigger or crashed the scheduler when mail configuration errors occurred.

### 🔍 Root Cause
1. **Lack of Daemon Queue Workers**: Manual period closing dispatches a queued job `ClosePeriodJob` to the background to avoid timing out HTTP requests. On shared hosting, there is no persistent daemon worker (such as Supervisor) running `php artisan queue:work`. Because of this, jobs in the `database` queue sit unprocessed forever, and the status remains stuck in `closing` indefinitely.
2. **Unhandled PHP Engine Errors (Throwable)**: In `PeriodAutoClose.php`, the try-catch blocks only caught `\Exception`. Unhandled PHP engine errors (such as email configuration errors, driver issues, or other `\Throwable` instances) during the email sending loops were not caught. This caused the scheduler execution to crash mid-transaction, preventing the database transaction from rolling back gracefully and stopping the command from completing with proper error diagnostics.

### 🛠️ Fix Applied
- **Scheduled Queue Worker**: Added `Schedule::command('queue:work --stop-when-empty')->everyMinute()->withoutOverlapping(5)->name('queue-work')` to `routes/console.php`. This automatically runs the queue worker via cron every minute to clear the queue database table, resolving stuck manual closing jobs.
- **Robust Exception Handling**: Upgraded the try-catch blocks in `PeriodAutoClose.php` to catch `\Throwable` instead of `\Exception`. This applies to both email loops and the outer transaction. Failed emails are now captured and logged with full error trace logs in `storage/logs/laravel.log` without crashing or rollback of the entire database transaction, and any main transaction exceptions are rolled back properly and logged.
- **Automated Tests**: Updated `PeriodAutoCloseTest.php` with a new test case `test_auto_close_catches_throwable_on_mail_failures` to assert that throwing a `Throwable` inside the mail loops does not interrupt or fail the command, and is properly logged.

## 7. Uploaded Logo and Favicon returning 404/500 (Symlink and Disk Routing Conflict)

### 📌 Problem Details
When uploading a logo or favicon, the image did not render in the browser and the link resulted in a 404 Not Found error (or a 500 Server Error when attempting to link via `storage-link.php` script).

### 🔍 Root Cause
1. **Broken/Disabled Symlinks**: Shared hosting environments (Hostinger) often disable native symbolic links (`symlink()`) for security reasons. Without a working symbolic link from `public/storage` to `storage/app/public`, Laravel's public asset URLs return 404.
2. **Local Storage Routing Hijack**: In `config/filesystems.php`, the private `local` disk was configured with `'serve' => true`. Since no `'url'` was set on it, Laravel's FilesystemServiceProvider automatically mapped the `/storage/{path}` route prefix to serve files from the private `storage/app/private/` folder. This route checked for signed URLs/signatures and returned a `403 Forbidden` for all public file requests, preventing any custom routing overrides or fallback handlers from responding.
3. **Link Script Crashing (500 Error)**: When visiting `storage-link.php` to fix the symlink, calling `symlink()` or `Artisan::call('storage:link')` on a server where `symlink()` is disabled causes Laravel's error handler to convert the PHP warning into an exception, terminating the script with a `500 Server Error`.

### 🛠️ Fix Applied
- **Disabled Private Disk Server**: Set `'serve' => false` on the private `local` disk in `config/filesystems.php` to prevent it from hijacking the public `/storage` url prefix.
- **Secure Storage Fallback Route**: Added a fallback route `Route::get('storage/{path}')` in `routes/web.php` that intercepts public file requests under `/storage` when the physical `public/storage` symlink is missing or disabled. The route validates files directly from the public storage disk and returns them safely using `response()->file()`.
- **Directory Traversal Protection**: Implemented strict security checks inside the fallback route (rejecting `..` and `\` characters, and verifying absolute paths with `realpath` and `str_starts_with`) to completely prevent Path Traversal attacks.
- **Automated Tests**: Created `StorageFallbackTest.php` containing tests that verify the fallback route successfully serves files from the public disk, returns 404s for missing files, and blocks traversal attacks.

## 8. Arabic and English Translation Updates & Seeder Realignment

### 📌 Problem Details
Some translation keys used in the React frontend were missing from the backend seeder file, causing fallback values to be displayed. Furthermore, translations inside the live database needed to be updated and fully synchronized with the seeder records to correct some old/incorrect values.

### 🔍 Root Cause
1. **Missing Keys**: 7 translation keys relating to manually verifying website tracking statuses in the admin dashboard and showing tracking codes were present in the frontend JS files but were missing in the backend seeder.
2. **Seeder Non-overwrite Logic**: The default seeder used `firstOrCreate()` which only inserted translations if they did not exist, preventing existing database entries from being updated or corrected.

### 🛠️ Fix Applied
- **Added Missing Keys**: Appended the 7 keys to `TranslationsSeeder.php` with precise English and Arabic values.
- **Key-to-Text Rewrite**: Generated clean, human-readable English strings directly from all key names in `TranslationsSeeder.php`, ignoring technical elements like `toast`, `btn`, `label`, etc. so that the values match their keys.
- **Arabic Translation Alignment**: Re-translated all formatted English labels to Arabic in batches using the Google Translate API and updated the Arabic values.
- **Enabled Database Overwriting**: Changed the database operation to `updateOrCreate()` to ensure existing database translations are overwritten and synchronized when seeding.
- **Created Browser-Based Seeder Utility**: Added `public/seed-translations.php` to let the administrator trigger database synchronization from their web browser.
